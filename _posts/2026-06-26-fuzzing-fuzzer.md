## 퍼징(fuzzing)
자동화된 소프트웨어 테스팅 기법으로 프로그램이 비정상적이거나 예상치 못한 입력값을 반복적으로 전달하여 오류나 취약점을 찾는다. 주로 크래시(Crash), 메모리 오류, 예외 처리 미흡, 보안 취약점 등을 발견하기 위해 사용된다.
<br>
### 퍼징의 기본 작동 원리
입력 생성 → 프로그램 실행 → 결과 관찰(Crash, Hang, Timeout, Sanitizer error)  → 문제 입력 저장 → 취약점 분석

## 퍼징의 종류
### 내부 정보 활용 정도에 따른 분류
#### 블랙박스 퍼징(Black-box Fuzzing)
프로그램 속을 보이지 않은 검은 상자로 간주하여 거기에 들어가고 나오는 입출력만 관찰하는 방식이다. 소스코드가 없어도 퍼징할 수 있고 구현이 간단하지만, 어떤 코드 경로가 실행되는지 알기 어렵고 비효율적인 입력이 많이 생성될 수 있다.

#### 그레이박스 퍼징(Grey-box Fuzzing)
프로그램의 내부 정보를 전부 활용하지 않고, 최소한의 실행 정보(*커버리지(Coverage))만 피드백으로 사용하는 방식이다. 효율과 현실성의 균형이 좋아 현재 가장 많이 사용되는 방식이지만, 프로그램 의미를 깊게 이해하지는 못한다.
<br>
<br>
*커저리지(Coverage): 주로 소프트웨어 개발에서 작성한 테스트가 전체 코드 중 얼마만큼을 실행했는지를 비율로 나타내는 측정 지표이다.

#### 화이트박스 퍼징(White-box Fuzzing)
프로그램을 마치 유리 상자처럼 투명하게 바라보며 내부 구조를 분석하고 실행 과정에서 발생하는 모든 정보를 활용하여 입력을 생성하고 검사를 수행하는 방식이다. 즉, 프로그램의 내부 구조와 실행 중 동작 정보를 모두 활용하여 프로그램을 심층적으로 분석하고 테스트를 진행하는 접근법이다. 깊은 경로 탐색에 유리하지만, 분석용이 크고 확장성이 낮을 수 있다.

### 입력 생성 방식에 따른 분류
#### 변이 기반 퍼징(Mutation-based Fuzzing)
기존 정상 입력(seed)에 일부 바이트를 바꾸거나, 삭제하거나, 추가하여 새로운 입력을 생성하는 방식이다. *seed corpus를 기반으로 동작하여 구현이 단순하고, 범용성이 높지만, 입력 형식이 복잡한 대상에서는 변형 결과가 쉽게 무효 입력이 될 수 있다.
<br>
<br>
*seed corpus: 소프트웨어 보안 테스트(Fuzzing)에서 테스트 및 분석을 시작하기 위해 사용하는 초기 입력 데이터 모음

#### 생성 기반 퍼징(Generation-based Fuzzing)
입력 데이터를 처음부터 새로 생성하는 방식으로, 파일 포맷, 네트워크 프로토콜, 직렬화 포맷, 스크립트 언어 등의 입력 형식에 대한 문법, 스키마(Schema), 프로토콜 명세와 같은 입력 모델을 미리 정의한 후, 이를 따르는 입력을 생성하는 방식이다. 조가 엄격한 입력을 대상으로 할 때 효과적이며, 문법적으로 유효한 입력을 생성할 수 있어 프로그램의 깊은 실행 경로까지 도달하기에 유리하지만, 입력 모델이나 문법을 직접 작성해야 하므로 초기 준비 비용이 많이 든다.

## 퍼저(Fuzzer)
소프트웨어 프로그램에 랜덤한 값을 입력하는 프로그램으로 퍼징 테스트 과정에서 사용되는 주요 도구이다.
### 주요 퍼저
#### AFL++
Google의 원본 AFL을 발전시킨 커뮤니티 기반의 상위 포크 프로젝트이자, 현재 가장 널리 쓰이는 범용 그레이박스 퍼저이다. 원본 대비 실행 속도, 뮤테이션 전략, 계측 방식이 대폭 개선되었으며, 소스코드 유무에 구애받지 않고 QEMU나 Frida 모드 등을 통해 바이너리 단독으로도 강력한 퍼징이 가능하다는 특징이 있다.
<br>
- 장점<br>
우수한 성능과 더불어 소스코드 유무에 구애받지 않는 높은 범용성을 제공한다. 활발한 오픈소스 커뮤니티를 통해 최신 퍼징 기법이 빠르게 도입되며, 사용자 정의 변이 규칙 및 플러그인을 활용한 강력한 확장성을 지원한다.
<br>
- 단점<br>
복잡한 구조로 인해 초기 설정과 타겟 분석 과정의 진입 장벽이 높다. 또한, 운영체제 종속성에 따른 제약이 존재하며 퍼징 구동 시 상당한 시스템 자원을 요구한다.

#### libFuzzer
LLVM 프로젝트에서 기본적으로 제공하는 LLVC/Clang 기반의 인프로세스 커버리지 가이드 퍼징 엔진이다. 퍼저와 대상 프로그램이 별개의 프로세스로 동작하는 기존 방식과 달리, 타겟 함수를 퍼저와 같은 프로세스 메모리 내에 링크하여 반복 호출을 한다는 특징이 있다.
<br>
- 장점<br>
새로운 프로세스를 매번 생성할 필요가 없으므로 속도가 매우 빠르고 사용법이 단순하며, 특정 라이브러리나 API 단위의 취약점을 찾는 데, 적합하다.
<br>
- 단점 <br>
구조화된 입력이 필요한 대상의 취약점을 찾는 것이 어려워 복잡한 커스텀 변환기나 추가 도구를 결합해야 하므로 복잡한 입력 구조의 한계를 가지고 있으며, 별도의 입력 없이 랜덤하게 바이트를 변형하기에 대상 프로그램의 구조나 규칙을 전혀 모르는 상태에서 유효한 데이터 생성하기까지 많은 시간이 소요될 수 있고, 메모리 부족이나 무한 루프에 빠지기 쉬워 Payload 길이 검증이 필요하다.

#### Jackalope
Google Project Zero에서 개발한 사용자 정의 및 커스터마이징이 가능한 분산형 코드 커버리지 기반 퍼저이다. Windows 및 macOS 환경에서 소스코드가 없는 블랙박스 바이너리를 타겟으로 최적화되어 있으며, 동적 계측 프레임워크인 TinyInst를 통해 메모리상에서 실행 흐름을 추적하고 대규모 병렬 처리를 지원한다는 특징이 있다.
<br>
- 장점<br>
소스코드를 확보할 수 없는 사용 소프트웨어를 분석하고 취약점을 발견하는 블랙박스 분석에 특화되어 있으며, 단일 시스템 내에서의 멀티 스레딩은 물론, 서버-워커(Server-Worker) 구조를 통한 다중 머신 분산 퍼징을 지원하여 방대한 데이터를 효율적으로 처리할 수 있는 대규모 병렬 및 분산 처리가 가능하다.
<br>
- 단점<br>
소스코드의 도움 없이 동작하므로, 퍼징 진입점과 구조를 파악하기 위해 디버거나 디스어셈블러를 활용하여 타겟 바이너리를 직접 분석해야 하여 높은 리버스 엔지니어링 역량이 요구되며, 주류 오픈 소스 도구인 AFL++에 비해 관련 문서, 튜토리얼, 트러블슈팅 사례 등 커뮤니티 기반의 레퍼런스가 부족하여 문제 발생 시 자체적인 해결 능력이 요구된다.

#### 주요 퍼저 비교
| 구분      | AFL++                   | libFuzzer                   | Jackalope                            |
| :-------- | :---------------------- | :-------------------------- | :----------------------------------- |
| 대상 범위  | 프로그램 전체 (실행 파일) | 라이브러리 / 특정 API (함수) | 블랙박스 바이너리 (주로 Windows/macOS) |
| 소스코드 필요성  | 선택 (있으면 유리, 바이너리 단독 지원) | 필수 (컴파일 및 빌드 제어권 필요) | 불필요 (소스 없는 바이너리 특화) |
| 동작 방식  | 프로세스 (Fork 기반)  | In-process (함수 단위) | In-process / Out-of-process |
